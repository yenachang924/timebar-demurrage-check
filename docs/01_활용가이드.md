# Claude 활용 가이드

두 참고 사례에서 가져온 방식이다.

- **네이버 사내 해커톤 1위 팀 (D2)**: 이긴 이유는 AI 기능 수가 아니라 입력 → 검증 → 판단 → 처리 → 결과가 하나로 이어진 것. 공식 숫자는 규칙으로 계산하고 AI는 초안·설명에 썼다. AI를 구현자뿐 아니라 평가자·검증자로 썼다.
- **현대차그룹 공모전 본선 (AI 직원 팀)**: 역할이 다른 에이전트가 근거를 달아 후보를 내고, 심사위원 페르소나가 블라인드 채점하고, "왜 1등을 못 하나"를 공격하는 에이전트가 약점을 먼저 찾았다. 사람은 방향과 `유지`/`다시`만 정했다.

## 역할 분담

| 내가 한다 | Claude가 한다 |
|---|---|
| 주제·판정 기준·예외 방침 결정 (`유지`/`다시`) | 후보·근거·반박 제시, 브리프 작성 |
| Studio에서 노드 배치·실행·내보내기·게시 | 노드 설계안, 프롬프트·스키마 초안, 출력 키 정의 |
| 실행 결과를 `work/runs/`에 붙여넣기 | 정답지와 대조, 틀린 케이스 원인 추적 |
| 문서가 진짜 업무 양식 같은지 최종 판단 | 가상 문서 HTML 작성 → PDF 변환, 저품질 변형 |
| 구글폼 제출, 승인 요청, Discord 질문 | 제출 전 정합성 검사, 체크리스트 |
| 발표, 영어 Q&A 답변 | 원고 초안, 예상 질문, 모의 심사 |
| API 키 입력, 결제 화면 | (하지 않음) |

Claude는 Studio 화면을 직접 볼 수 없다. 워크플로 JSON을 내보내 `submission/`에 넣거나 화면 캡처를 붙여주면 그때부터 검증할 수 있다.

## 명령

| 명령 | 언제 | 하는 일 |
|---|---|---|
| `/topic` | 주제를 못 정했을 때 | 후보 생성 → 탈락 기준 → 블라인드 채점 → 반박 → 상위안 |
| `/brief <주제>` | 주제 후보가 생겼을 때 | 9칸 브리프 작성 (`docs/brief.md`) |
| `/design` | 주제 확정 후 | 노드 구성·출력 키·예외 경로 설계 |
| `/dataset` | 설계 확정 후 | 케이스 표 → 문서 HTML → PDF → 정답지·유형표 초안 |
| `/precheck` | 무엇이든 바꾼 뒤, 제출 전 | 정합성 검사 + 독립 정답 재도출 |
| `/judge` | 설계·데이터가 한 판 돌았을 때 | 배점표대로 블라인드 채점 |
| `/attack` | `/judge` 직후 | "왜 1등을 못 하나" 공격 |
| `/pitch` | 11/26 저녁 | 영어 6분 원고 + 예상 질문 |

## 한 판의 순서

```
/brief → 내가 유지/다시 → /design → Studio에 구현 → 전체 실행
   → 결과를 work/runs/에 저장 → score.py → 틀린 케이스 수정
   → /precheck → /judge → /attack → 고칠 것 3개만 고르기 → 반복
```

점수가 문서 수정만으로는 어느 선에서 멈춘다. `/judge` 점수가 두 번 연속 제자리면 문서를 다듬지 말고 워크플로나 데이터 자체를 바꾼다.

## 심사에서 내가 직접 답할 수 있어야 하는 것

AI로 만들었어도 Q&A는 내 말로 답해야 한다. 아래 다섯 개는 원고 없이 답할 수 있게 준비한다.

1. 왜 이 업무인가 — 누가, 어떤 문서로, 무엇을 반복 판정하나
2. 왜 이렇게 나눴나 — 각 노드를 고른 이유, 한 노드에 몰지 않은 이유
3. 틀리면 어떻게 되나 — `검토 필요`로 빠지는 조건, 사람이 보는 지점
4. 카드에서 무엇을 바꿨나 — Use Case Explorer 대비 우리가 더한 것
5. 숫자의 근거 — 발표에 쓴 모든 수치의 출처
